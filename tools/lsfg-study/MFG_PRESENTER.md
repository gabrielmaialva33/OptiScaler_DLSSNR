# LSFG at x3 and x4: a presenter of our own (OPTI_INTEGRATION.md option a′)

Status: **built and running at x3 and x4 in PCSX2** (2026-10-13, branch `study/lsfg-d3d12`; results in section 9);
the multiplier is in the LSFG menu and changes live with our presenter, x2 included (2026-10-14; 1.4, 5, 9). Study only, like everything under `tools/lsfg-study/`: nothing
here merges into `dlss-neural-rendering` (OPTI_INTEGRATION.md, "Read this first").

Citations are `file:line` against this worktree. Two abbreviations, as in OPTI_INTEGRATION.md:

- **FISC** = `external/FidelityFX-SDK-v2/Kits/FidelityFX/framegeneration/fsr3/dx12/FrameInterpolationSwapchainDX12.{h,cpp}`
  (SDK 2.3.0, the version of the signed DLLs in use; MIT, `external/FidelityFX-SDK-v2/docs/license.md`).
- **FSRFG** = `OptiScaler/framegen/ffx/FSRFG_Dx12.cpp`.

## Summary

- **Why a fork.** FFX's swapchain asks for one generated frame (`FISC.cpp:1927`), holds one generated and one real
  frame per present in its pacing record (`FISC.h:45-50`, `:89`), double-buffers one output (`FISC.h:43`) and spaces
  presents by half the real frame time (`FISC.cpp:883`). None of that is configurable from outside the signed DLL.
- **What.** A copy of FISC, its helpers, its UI composition and its debug pacing lines, under
  `retoque/lsfg/presenter/`, with AMD's MIT notice kept on every file. De-templated (one concrete class instead of
  three ABI instantiations), widened to N generated frames per real frame, N = `[LSFG] Multiplier` − 1, 1 to 3.
- **When.** Only when `[LSFG] Enabled=true` and `[LSFG] Multiplier` is 3 or 4 at the moment the first FG swapchain of
  the process is created. Otherwise FSR-FG keeps FFX's swapchain, byte for byte as today (x2, option (b)).
- **How it is reached.** FSRFG's two swapchain-creation sites create ours instead of FFX's swapchain context, and
  the FSRFG calls that reach a swapchain go through a drop-in router that forwards to `FfxApiProxy` unless the
  context or swapchain is ours. FFX's FG context stays as the fallback interpolator, configured so that it never
  touches a swapchain.
- **How frames are asked for.** Exactly FFX's callback contract, widened: one `ffxDispatchDescFrameGeneration` per
  real frame with `numGeneratedFrames = N` and `outputs[0..N-1]`; the callback returns with `numGeneratedFrames` set
  to what it wrote. LSFG already loops `k = 1..N` at timestamps `k/(N+1)` (`retoque/lsfg/LsfgFrameGen_Dx12.cpp:1027-1035`,
  `LsfgGraph.h:389`). That is the narrow interface; OpenCode's MFG work plugs in behind it.

### 1.2 Dropped

- **The three ABI instantiations** (`FISC.h:421-423`), `FfxAbiFrameGenSwapChainCall`, the SDK1 present-callback
  shims and `IID_AMDFFXABIVersion`. They exist so that FFX's provider DLL, built from some other SDK, can drive a
  swapchain made by another. Nothing outside OptiScaler.dll drives ours.
- **`IFrameInterpolationSwapChainDX12` and `IID_IFfxFrameInterpolationSwapChain`.** Our `QueryInterface` answers
  only the DXGI interfaces and an IID of our own. FFX's FG provider asks for those two IIDs before it calls into a
  swapchain (`ffx_provider_fsr3framegeneration.cpp:243`, `FISC.cpp:120-158`), so the signed DLL can never cast our
  object to its types. That is what makes the pacing record free to change (1.4).
- **The registered interpolation command list** (`getInterpolationCommandList`, `registeredInterpolationCommandLists`,
  `FISC.cpp:1906-1915`, `:2559-2594`) and `interpolationOutput()`: reached only through FFX's swapchain query API,
  which OptiScaler's FSR-FG output does not use.
- **AntiLag 2 frame-type marking** (`FISC.cpp:682-700`): AntiLag 2 is AMD-only and reads private data the swapchain
  would have to own.

### 1.3 Kept, with one fix

Everything else is FISC's code path for path: replacement backbuffers, the present queue, the interpolation thread
and the presenter thread, the frame-latency waitable object and its semaphore thread, UI composition, resize,
fullscreen, HDR metadata, colour space. The one change beyond widening: FISC keeps the UI composition's PSOs and
descriptor heaps in file statics (`_UiComposition.cpp:44-51`), released by whichever swapchain shuts down first. A
game that makes a second swapchain before releasing the first (FG_Hooks.cpp:311-327) would have the old one's
destructor free them under the new one's presenter thread. Here they belong to the swapchain and are released in its
`shutdown()`, after `waitForPresents()` and after both threads have exited.

### 1.4 Only for x3 and x4, latched per process

**Why not for every LSFG mode.** Invariant 1 (DEVELOPMENT.md): at its default, a new feature leaves the old path
byte-identical. x2 through FFX's swapchain is measured and validated (Divinity, PCSX2); a fork exercised for the
first time must not replace it. So `Multiplier=2`, the default, never constructs our presenter.

**Why latched.** `FGHooks::HookFGSwapchain` detours the FG swapchain's methods once per process, by code address
(`OptiScaler/hooks/FG_Hooks.cpp:517-597`, guarded by `o_FGSCPresent != nullptr` at `:519`). Whichever class backs the
first FG swapchain is the one whose `Present`, `ResizeBuffers` and `Release` carry OptiScaler's FG logic for the rest
of the process. A later swapchain of the other class would present with no `FGPresent` at all. So the choice is made
at the first FG swapchain creation and kept: `Lsfg::Presenter::Wanted()` reads `[LSFG] Enabled` and `Multiplier` once
and logs the decision. With FFX's swapchain latched, a later 3 or 4 is logged as taking effect after a restart.

**Inside our presenter, the multiplier is live, 2 included.** The router reads `Enabled` and `Multiplier` at every FG
configure, which FSRFG's `Dispatch` makes once per real frame (`:530`), and hands the swapchain
`GeneratedFramesLive(enabled, multiplier)` (`presenter/MfgLatch.h`): N = multiplier − 1 with LSFG on, 1 with it off.
The swapchain reads N at its next present. Multiplier 2 is N = 1 through the fork, and that is FFX's x2 on every axis
that matters:

- **Pacing.** Two presents per entry, each `avg/2 − σ·vf − margin`: `PresentDelta` at two frames is FFX's formula bit
  for bit (`tests/lsfg-presenter`, over a grid, and again for `GeneratedFramesLive(true, 2)`).
- **The request.** One output, `numGeneratedFrames = 1`, LSFG's main pass at `Timestamp = 1/2`: what FFX's swapchain
  asks for. LSFG reads N per call (`LsfgFrameGen_Dx12.cpp`, `TimestampFor(k + 1, io.generatedFrames)`), so nothing in
  it is sized for the multiplier the process started with.
- **UI composition and counting.** One composition per presented frame, generated or real, as at any N (3.5); the
  presenter's summary and LSFG's count frames per entry.
- **Not new code.** N = 1 is already what our presenter runs whenever FFX interpolates in LSFG's place (warm-up, a
  refusal, LSFG switched off): `Lsfg::TakesFrame` lowers the request to 1 (4.1).

What it does not have is what the fork dropped (1.2): AntiLag 2 frame-type marking. Outputs made for a higher N stay
until the next resize or shutdown (3.3). After a restart with 2 saved, the process runs FFX's own swapchain again.

| Started at (first FG swapchain) | Choose 2 | Choose 3 | Choose 4 |
|---|---|---|---|
| 2, or LSFG off: **FFX's swapchain** | runs (x2) | saved, x2 until a restart | saved, x2 until a restart |
| 3 or 4: **ours** | x2 from the next frame (N = 1) | x3 from the next frame | x4 from the next frame |
| no FG swapchain yet | the latch reads it | the latch reads it | the latch reads it |

`tests/lsfg-presenter` holds `MfgLatch.h` to this table, and the menu (5) and the router read it from there.

## 2. How OptiScaler creates it instead of FFX's swapchain

### 2.1 Creation

FSRFG's two creation sites (`FSRFG_Dx12.cpp:1155`, `:1199`) call `FfxApiProxy::D3D12_CreateContext` with a
`ffxCreateContextDescFrameGenerationSwapChainNewDX12` or `...ForHwndDX12`. Each becomes

```cpp
auto result = Lsfg::Presenter::Wanted() ? Lsfg::Presenter::CreateSwapChain(realFactory, realQueue, desc, swapChain, &_swapChainContext)
                                        : FfxApiProxy::D3D12_CreateContext(&_swapChainContext, &createSwapChainDesc.header, nullptr);
```

`CreateSwapChain` does what FFX's provider does (`ffx_provider_fsr3framegenerationswapchain_dx12.cpp:115-147`): it
builds the swapchain (refcount 1, the game's), `AddRef`s it for a context record of ours (refcount 2) and stores that
record's address in `_swapChainContext`. FFX's `DXGI_SWAP_CHAIN_DESC` → `DESC1` conversion (`FISC.cpp:489-521`)
comes along.

It runs inside `FGHooks::CreateSwapChain`'s `ScopedSkipFGSCCreation` (`DxgiFactory_WrappedCalls.cpp:216`), so the real
swapchain it creates on its present queue goes through OptiScaler's factory hook as FFX's does and comes back as a
`WrappedIDXGISwapChain4`: the menu overlay and NR's wrapped-swapchain entry see every present, generated ones
included, exactly as with FFX.

The game receives our object directly (`DxgiFactory_WrappedCalls.cpp:217-222`); `SetFGSwapchain` registers it as
`currentFGSwapchain` and detours its methods.

### 2.2 The calls that reach a swapchain

`_swapChainContext` now holds our record, and FFX's DLL must never receive it. Every FSRFG call that may reach a
swapchain goes through a drop-in with `FfxApiProxy`'s signature:

| FSRFG site | Call | Ours |
|---|---|---|
| `ConfigureFramePaceTuning` (`:294`) | `D3D12_Configure(&_swapChainContext, KEYVALUE key 2)` | `setFramePacingTuning` |
| `Dispatch` (`:430`) | `D3D12_Configure(&_swapChainContext, REGISTERUIRESOURCE)` | `registerUiResource` |
| `Dispatch` (`:529`), `CreateContext` (`:1286`), `Activate` (`:1428`), `Deactivate` (`:1472`) | `D3D12_Configure(&_fgContext, FRAMEGENERATION{swapChain = _swapChain})` | see below |
| `Dispatch` (`:536`) | `D3D12_Configure(&_fgContext, GLOBALDEBUG1)` | forwarded unchanged |
| `ReleaseSwapchain` (`:1244`) | `D3D12_DestroyContext(&_swapChainContext)` | releases our reference |
| `DestroyFGContext` (`:1094`), `CreateContext` (`:1273`) | `D3D12_DestroyContext(&_fgContext)` | forwarded unchanged |

`Lsfg::Presenter::D3D12_Configure` and `D3D12_DestroyContext` forward to `FfxApiProxy` untouched unless the context
is one of our records, or the descriptor is an `ffxConfigureDescFrameGeneration` whose `swapChain` is one of our
swapchains. A record found is pinned under the registry lock and the lock is dropped before the swapchain is called;
`D3D12_DestroyContext` erases the record under the lock and waits for the pins to go before it drops the record's
reference. The lock is never held across a call into the swapchain, because a configure can wait for the presenter
thread, and the presenter thread can reach FSR-FG's `Deactivate` (`MenuOverlayDx::CleanupRenderTarget`), which comes
back through the router. With FFX's swapchain in use, the router compares two pointers against an empty registry and forwards:
the x2 path takes the same calls with the same arguments.

**The FG context, when the swapchain is ours.** The router copies the descriptor, ORs
`FFX_FRAMEGENERATION_FLAG_NO_SWAPCHAIN_CONTEXT_NOTIFY` into the copy's flags and forwards the copy to FFX. With that
flag FFX's provider skips its ABI probe and its swapchain configure (`ffx_provider_fsr3framegeneration.cpp:241`,
`:440`) but still records the callbacks, `frameGenEnabled`, the HUD-less resource and `lastConfigureFrameID`, which
its own interpolation dispatch checks (`:566-569`). The router then hands our swapchain the same configuration FFX's
provider would have built (`:216-436`): enabled, async, flags, `onlyPresentGenerated`, generation rect, frame ID,
debug pacing lines, and the two callbacks, called directly instead of through FFX's per-frame-ID trampolines.

**Do we still need FFX's FG context?** For LSFG frames, no: LSFG reads only the presented frame, and FFX's prepare is
already skipped on frames LSFG takes (FSRFG `:539-540`). It stays because FSR-FG's state machine is built on it
(`Dispatch` returns early without it, `:332`; `Activate`/`Deactivate` configure it) and because FFX's interpolation
is the fallback while LSFG's shaders build, after a refusal (HDR10, scRGB, unsupported formats) or when the user
switches LSFG off in the menu. Its idle VRAM is option (b)'s known cost (OPTI_INTEGRATION.md risk 3).

### 2.3 What else sees the swapchain

- `IFGFeature_Dx12::CreateSwapchain*` (`IFGFeature_Dx12.cpp:538-628`) and `hkFGRelease` (`FG_Hooks.cpp:1572-1684`)
  use only DXGI methods and `ReleaseSwapchain`. `hkFGRelease` releases the game's extra references to
  `GetBuffer` results down to one: ours, as with FFX.
- `FSRFG_Dx12::Present`'s UI blit (`:1992`) calls `GetCurrentBackBufferIndex`/`GetBuffer` on `_swapChain`: our
  replacement buffers.
- `DlssNr::RunPresentPass(This)` in `FGPresent` (`FG_Hooks.cpp:1444`) edits our replacement backbuffer before our
  `Present` copies it: generated frames carry the NR edit, as with FFX.
- `SwapchainContext()` is used as an identity token by the D3D11 bridge (`dx11_with_dx12_sc.cpp:267`, `:512`, `:628`)
  and as a non-null test by the wrapped swapchain's release (`wrapped_swapchain.cpp:745`): our record serves both.

## 3. Widening to N

### 3.1 The pacing record

We own both sides now, so the "no modifications ... ABI stability" rule (`FISC.h:52`, `:68`) no longer applies:

```cpp
struct FrameInfo { bool doPresent; bool generated; FfxApiResource resource; UINT64 interpolationCompletedFenceValue;
                   UINT64 presentIndex; UINT64 presentQpcDelta; };
struct PacingData { ...FISC's fields...; uint32_t frameCount; FrameInfo frames[kMaxGeneratedFrames + 1]; };
```

`frames[0..k-1]` are the k generated frames in display order, `frames[k]` the real one. `kMaxGeneratedFrames = 3`
(x4). Both threads loop over `frameCount` instead of `FrameType::Count`.

### 3.2 Pacing: real frame time / (frames per real frame)

FISC measures the real frame interval on the interpolation thread (the time between successive interpolation-fence
completions, a 10-sample moving average with its standard deviation, reset after a gap over 100 ms or on a reset;
`FISC.cpp:863-879`) and gives every present of the entry the same delta from the previous present:

    delta = avg × 0.5 − σ × varianceFactor − safetyMargin          (FISC.cpp:882-886)

The fork divides by the number of frames the entry presents instead of 2:

    delta = avg / numFramesToPresent − σ × varianceFactor − safetyMargin

- x4 with three generated frames: `avg/4` between every present, so 30 fps real gives 120 presents per second.
- An entry with no generated frame (LSFG warm-up, a reset, FFX's fallback producing one at most) presents its real
  frame `avg/1` after the previous present: the cadence of the real frames stays even, where FISC would show it after
  half a frame.
- The variance and margin terms stay per present, as in FISC: the cycle ends `(k+1)(σ·vf + margin)` short of `avg`,
  which is the slack that keeps the presenter from locking the game to a lower rate (FISC's comment at `:881`). It is
  larger than at x2 by design; OptiScaler's `FGFPTVarianceFactor`/`FGFPTSafetyMarginInMs` still tune it.

**Back-pressure is unchanged.** The game's next `Present` waits for the CPU composition fence of every frame of the
previous entry (`FISC.cpp:2172`), and the presenter composites the real frame only after presenting the generated
ones. So an entry is never overwritten while the presenter is busy with the one before (the drop path at `:744-746`
stays for safety), and the game cannot run ahead of the display.

### 3.3 Generated-frame slots

FISC double-buffers one output (`FISC.h:43`, `:289`): present p writes `interpolationOutputs[p % 2]`, which becomes
available again when the composition of the frame shown from it completes (`:1903-1904`, `:2014`). The fork keeps two
**sets** of `kMaxGeneratedFrames` outputs, `outputSets[p % 2][k]`, and one availability value per set: the present
index of the set's last generated frame. Composition is in order on one queue, so that value covers all of them.

Outputs are created on demand up to the current N (in the display format, with `ALLOW_UNORDERED_ACCESS`, in
`UNORDERED_ACCESS`, as FISC's: `:1068-1086`). A higher multiplier adds outputs at the next present; a lower one keeps
them until the next resize or shutdown, so nothing is freed while the GPU may read it. At 3440x1440 RGBA8 that is
2 × 3 × 19.8 MB at x4 against FISC's 2 × 19.8 MB.

### 3.4 Waitable object, frame latency, buffers

- The game's frame-latency semaphore is released once per game present, when the last frame of its entry has been
  composited (`SignalFrameLatencyWaitableObject` on `compositionFenceGPU`, `FISC.cpp:2192`). Unchanged with N.
- The real swapchain keeps FISC's three flip-discard buffers (`FISC.cpp:1262`): the presenter waits for each
  composition before it presents (`:773`), so with a 165 Hz display and tearing allowed, three are enough for four
  presents per real frame. Measured, not assumed (section 7).
- The command pool grows from 32 to 64 entries per queue type: each real frame now takes one interpolation list,
  up to N + 1 composition lists and as many debug-pacing lists, and the pool's DIRECT bucket is shared by the game
  queue and the present queue (`_Helpers.h:241-293`). FISC asserts on exhaustion; the fork waits for the oldest entry
  instead of dereferencing null.

### 3.5 UI composition per generated frame

`compositeSwapChainFrame` (`FISC.cpp:619-670`) already runs once per presented frame with `isGeneratedFrame` set: the
registered UI layer (`[FrameGen] SynthesizedHudLayer`, FSRFG `:415-430`) is drawn over each of the N generated frames
and the real one. The descriptor ring holds 32 compositions (`_UiComposition.cpp:44`) and the presenter waits for each
composition's GPU fence before presenting it (`:773`), so at most one composition is in flight: the ring cannot be
reused under the GPU at any N. OptiScaler's reprojection present callback (FSRFG `:711-847`) assumes one generated
frame half-way; with our presenter it is called N times and is not adapted (section 8).

### 3.6 Reset, resize, fullscreen

- **Reset.** `frameInterpolationResetCondition` is set on enable and after resource destruction and cleared by the
  first entry with a generated frame, as in FISC; it resets the pacing average (`presentInfo.resetTimer`) and goes
  to the callback as `desc.reset`.
- **Resize.** `ResizeBuffers` → `destroyReplacementResources()` (`FISC.cpp:1547-1640`): under the critical section,
  `waitForPresents()` (game, interpolation and present fences), stop both threads, release the replacement buffers,
  **both output sets, every slot**, and the UI copy, reset the counters and fences, restart the threads. Then the
  real `ResizeBuffers`. `GetBuffer` recreates on demand (`:2224-2246`).
- **Fullscreen.** `SetFullscreenState`/`GetFullscreenState`/`ResizeTarget` forward to the real swapchain, as in
  FISC; OptiScaler's hooks around them (`FG_Hooks.cpp:598-680`, `:937-953`) deactivate FG first, as with FFX.
- **Shutdown.** FISC's order (`FISC.cpp:1275-1335`), plus the per-swapchain UI composition and debug pacing objects
  released after the threads have exited and the queues drained.

## 4. Asking LSFG for N frames

### 4.1 The contract

`dispatchInterpolationCommands` fills one `ffxDispatchDescFrameGeneration` (`ffx_framegeneration.h:84-97` of the
ffx-api the build uses) per real frame:

| Field | Value |
|---|---|
| `commandList` | an interpolation list from the pool, on the game queue, or on the async compute queue with `[FrameGen] FGAsync` |
| `presentColor` | the replacement backbuffer the game rendered, in `PRESENT` |
| `outputs[0..N-1]` | this present's output set, in `UNORDERED_ACCESS` |
| `numGeneratedFrames` | N on entry; **on return, how many of `outputs[]` were written** (0..N) |
| `reset`, `backbufferTransferFunction`, `minMaxLuminance`, `generationRect`, `frameID` | as FISC (`:1926-1932`) |

The callback is FSRFG's `DispatchCallback` (`:849-1064`), unchanged: its reset policy, cancellation and HUD helpers
run as before, then `Lsfg::TakesFrame` decides who interpolates (`:1057`).

- **LSFG takes the frame.** `Lsfg::FfxDispatch` records ingest, the pre-pass once, and for `k = 1..N` the main pass
  with `Timestamp = k/(N+1)` writing `outputs[k-1]` (`LsfgFrameGen_Dx12.cpp:1022-1062`), and sets
  `numGeneratedFrames` to N, or to 0 while warming up or after a reset. This loop exists since `3777af9b`; with FFX's
  swapchain it only ever ran with N = 1.
- **FFX interpolates instead** (LSFG building, refused, or switched off). FFX's dispatch writes `outputs[0]` only and
  leaves `numGeneratedFrames` as it found it (`ffx_provider_fsr3framegeneration.cpp:561-640`). So `Lsfg::TakesFrame`,
  fork-owned, lowers `numGeneratedFrames` to 1 whenever it hands the frame to FFX: our presenter then shows x2 for
  that frame instead of stale outputs. With FFX's swapchain the value is already 1, so nothing changes there.

**OpenCode's MFG work** (`tools/lsfg-study/MFG_CONTRACT.md`, merged from `study/lsfg-mfg-gen` in `d3f1b108`) offers
two modes. The presenter uses **Batch mode through `FfxDispatch`** (`numGeneratedFrames = K`, `outputs[0..K-1]`, one
list), which that contract names as the alternative to `RecordBatch`, and which keeps FSR-FG's per-frame latch: the
latch decides whether FFX's prepare ran, so a presenter that called `RecordBatch`/`RecordGenerated` directly would skip
`DispatchCallback`'s reset policy and could leave FFX interpolating a frame it never prepared. Sequential mode
(`RecordGenerated`, one list per frame) is the route to the per-frame fences of 4.2, if they are ever wanted; it
records no GPU timestamps and does its own history keeping, so it would need the latch wired through it first.

### 4.2 Lists, queues, synchronisation

All N frames are recorded into **one** list and signal **one** interpolation fence (FISC's model: `:1917-1939`). The
first generated frame therefore waits for all N: about N × 0.8 ms on PCSX2 (OPTI_INTEGRATION.md, second step),
inside a 33 ms real frame. Splitting would need one list per frame, which means a callback per frame and a contract
LSFG does not have; it is an optimisation to measure later, not a correctness need.

The order, as in FISC, widened:

1. Game queue signals `gameFence`; the interpolation queue waits for it (`:1960-1961`): the list sees the game's
   frame and NR's edit.
2. The interpolation queue waits for `compositionFenceGPU ≥` the set's availability (3.3), runs the list, signals
   `interpolationFence`.
3. The interpolation thread waits for that fence on the CPU, measures the real interval, sets every frame's delta
   (3.2) and hands the entry to the presenter thread.
4. The present queue waits for `interpolationFence` before compositing a generated frame (`:624-625`); each
   composition signals `compositionFenceGPU`/`CPU` with its present index; the presenter waits for it, then for the
   pacing target, then presents.
5. The game's next `Present` waits for the previous entry's compositions (`:2172-2174`) and for the previous
   interpolation (`interpolationEvent`, `:2188`), so LSFG's per-frame descriptor writes never race a list still in
   flight (its output ring, `LsfgFrameGen_Dx12.h:228-236`, is 8 slots for at most 3 per list).

## 5. Config

`[LSFG] Multiplier`, an int: 2 (default), 3 or 4; anything else is ignored at load (default 2). Four points
(DEVELOPMENT.md rule 4): `CustomOptional<int> LsfgMultiplier { 2 }` in `Config.h`'s LSFG block, `readInt` with the
range check in `Config.cpp`, `GetIntValue` on save, `Multiplier=auto` in `OptiScaler.ini`'s `[LSFG]` section, plus
`Config.md`. `tests/lsfg-integration` round-trips it with the other LSFG keys.

**Menu.** A **Multiplier** combo in the LSFG block of the FSR FG card (`retoque/lsfg/LsfgMenu.cpp`), after
Performance Mode and disabled with it while LSFG is off, as its siblings are. It writes `LsfgMultiplier` only when the
selection changes, so an untouched 2 stays unset and saves as `auto`; OptiScaler's Save Settings writes it like any
key. Each item says what choosing it does now, from the table in 1.4:

- **Started at 3 or 4** (ours): `2x`, `3x`, `4x`; every choice applies at the next real frame.
- **Started at 2, or with LSFG off** (FFX's): `2x`, `3x (after a restart)`, `4x (after a restart)`. With 3x or 4x
  chosen, an amber note under the combo says what runs and what to do: "Now 2x: the game started with FFX's swapchain,
  which shows one generated frame. Save Settings and restart the game for 3x."
- **Ours, 3x or 4x chosen, LSFG not generating** (building its shaders, or refusing the frame): "Now 2x, while FFX
  interpolates in LSFG's place (see Status)", because FFX writes one frame (4.1).

Not a dead control (rule 2): with FFX's swapchain, a 3x or 4x is a choice for the next start, saved like any other
key, and the item and the note say so instead of pretending it acted. The text goes through `Localization` with pt-BR
entries, as the rest of the LSFG block now does (`tests/nr-localization` scans `LsfgMenu.cpp`).

## 6. Log lines

- Once, at the first FG swapchain: `LSFG presenter: [LSFG] Multiplier 3: our frame-generation swapchain replaces
  FFX's for this process (N generated frames per real frame)` or `... Multiplier 2: FFX's swapchain (x2), unchanged`.
- Every 10 s while our presenter runs: `LSFG presenter: last 10.0 s: R real + G generated presented (G/R per real;
  entries by generated count 0:a 1:b 2:c 3:d), P fps presented over R/10 fps real, present interval p50/p99 (target
  t ms), share over 1.5 × target`. Intervals are QPC between consecutive `Present` calls on the presenter thread.
  This is the proof of N generated frames per real frame and the measured presented rate.
- LSFG's own summary counts generated frames, not base frames, and names the multiplier.
- When the multiplier changes with our presenter: `LSFG presenter: xM from frame F (N generated frame(s) per real
  frame)`, at the configure that hands the swapchain the new N.
- When the config asks for the other swapchain than the one latched, once per Enabled/Multiplier pair: with ours, `LSFG presenter:
  [LSFG] Enabled true, Multiplier 2: x2 from the next frame through our presenter (one generated frame); FFX's own
  swapchain only from the next start`; with FFX's, `LSFG presenter: [LSFG] Enabled true, Multiplier 3 asks for our
  presenter, but this process runs FFX's swapchain (x2); x3 takes effect after a restart`.

## 7. Validation (phase 2)

PCSX2 (`~/Games/pcsx2-nr-test/run.sh`, native D3D12 under vkd3d-proton, synthesized input, NR on), at x3:

1. The latch line, LSFG's context line and its first frame showing `2 generated frame(s) asked`.
2. The presenter summary: `2.00 per real`, presented rate ≈ 3 × real rate, intervals around `avg/3`.
3. No `DEVICE REMOVED`, no vkd3d-proton errors in `steam-0.log`, a clean shutdown.
4. Then x4, and `Multiplier=2` (FFX's swapchain, today's path) as the control.

**One more difference from FFX: identical-code folding.** FGHooks detours our methods by code address
(`FG_Hooks.cpp:517-597`). FFX's swapchain is in its own DLL; ours shares OptiScaler.dll with other DXGI wrappers, and
Release links with `/OPT:ICF`. A pure forwarder of ours (`ResizeTarget`, `Set/GetFullscreenState`,
`GetFullscreenDesc`), or a `Release` with the same refcount offset, could be folded with another class's identical
function, and the detour would then catch that class too. Each hooked forwarder starts with a `__nop()` no other
forwarder has (`LSFG_MFG_UNFOLDABLE`); `tests/lsfg-presenter` checks it.

## 8. Risks

1. **Pacing at 165 Hz with VRR off** (the workstation profile's decision; never changed here). With vsync, presents
   snap to 6.06 ms vblanks: 90 fps (x3 of 30) alternates one and two refreshes, 120 fps (x4) too, and judders either
   way; no multiplier of a 30 fps base divides 164.89 Hz. With tearing allowed (PCSX2 runs `VsyncEnable=false`, and
   the presenter sets `ALLOW_TEARING` when supported, `FISC.cpp:677-680`), the cadence follows the QPC pacer exactly
   and tears instead. Only the interval statistics in section 6 say which is better on this display.
2. **Latency.** The real frame is shown about N/(N+1) of a real frame after it was rendered, plus the generation time
   of all N frames: x2 holds it half a frame, x4 three quarters. Inherent to interpolation; the presenter adds no
   queueing beyond FISC's.
3. **Proton against Windows.** vkd3d-proton does not validate D3D12 (CLAUDE.md, "Proton is not a D3D12 validator").
   The fork's D3D12 usage is FISC's, which runs on Windows as shipped, but the widened state (six outputs, more lists
   in flight) needs a run with the debug layer on native Windows before anyone else runs it.
4. **Same-class latch.** Started at 2 (or with LSFG off), a 3 or 4 chosen in the menu waits for a restart: FFX's
   swapchain cannot show it. Logged, and the menu says so (5). Started at 3 or 4, every value applies live (1.4).
5. **FFX fixes stop flowing in.** The fork is SDK 2.3.0's FISC; an FFX fix to its swapchain must be ported by hand.
   The file mapping in 1.1 keeps function names, so a diff per function is possible.
6. **Reprojection** (`[FrameGen] ReprojectionEnabled`) assumes one generated frame at t = 0.5 (FSRFG `:798`). With
   N > 1 it runs per generated frame with the wrong t. Untested and unsupported at x3/x4.
7. **Inputs other than synthesized.** Games with their own FSR-FG or DLSS-G inputs reach the same callback but were
   never run with our presenter. `IFGFeature::GetInterpolatedFrameCount` (used by the frozen-feature check and the
   latency markers) still reports 1.
8. **The UI composition PSO is built for the first backbuffer format** and not rebuilt when a resize changes the
   format (FISC behaves the same, `_UiComposition.cpp:200-206`). An HDR toggle mid-session with a UI layer would draw
   with a stale PSO.

**Open problems.**

1. **PCSX2 makes a second swapchain on a new window** about 4 s in, without releasing the first. FSR-FG's
   `CreateSwapchain1` only releases an old swapchain for the same window (`IFGFeature_Dx12.cpp:584-628`), and
   `hkFGRelease` swallows releases of the old one, so the first swapchain (FFX's or ours) is never destroyed and keeps
   its idle threads and buffers for the session. Upstream behaviour, not this fork's; with our swapchain it costs two
   idle threads, the replacement buffers and the outputs of the first size.
2. **Pacing on this display with vsync.** These runs tear (PCSX2 asks for `SyncInterval 0`). With vsync at 164.89 Hz,
   neither 90 nor 120 fps divides the refresh, so presents will alternate one and two vblanks; not measured yet.
3. **Native Windows**, the D3D11 bridge (Divinity) and the inputs other than synthesized are not run (8.3, 8.7).
4. **AntiLag 2 frame-type marking** was dropped with the fork (1.2). FFX's presenter tells the AntiLag 2 context
   OptiScaler injects into the real swapchain whether each present is generated; ours does not, so OptiScaler's
   low-latency emulation sees every present as real at x3/x4. On this machine the call fails anyway in the x2 control
   (`AmdExtAntiLagApi ... LowLatencyUpdateFail`, NVIDIA); on AMD it would matter.
5. **All N frames in one list**, so the first generated frame waits for the last: about 0.4 ms per extra frame here.
